# Handoff: v2.3 — stack control, and retiring Dockge

Builds on `V2.2-LAUNCH-LINKS-AND-WIDGETS.md`. One addition that **replaces the Dockge container**:
the stack drawer v2.2 introduces gains the two controls Dockge is actually used for — bring a
stack up or down, and edit its compose file.

**This adds no capability.** Every step it needs already exists, is risk-classed, and is covered
by the execution gate:

| Dockge does | Step we already have | Risk |
| --- | --- | --- |
| Start a stack | `stack.up` | R1 |
| Stop a stack | `stack.down` | R2 |
| Restart one service | `service.restart` | R1 |
| Edit a compose file | `compose.write` → `stack.up`, via `edit_runbook()` | R3 |
| Read logs | container detail, shipped | — |
| Update an image | `update.canary` — with automatic rollback, which Dockge has no notion of | R2 |

So the security surface does not move: no new step type, no new sudo grant, no change to
`policy.py`. What is missing is entirely UI. Today the dashboard can propose exactly two things —
a container restart from the detail view, and a restart from an incident row. Everything else
arrives through the planner or Telegram.

**Do not build the rest of Dockge.** No terminal, no per-container env editor, no image browser,
no stack creation wizard. The two controls above plus what is already shipped is the whole scope.

---

## 1 · Stack controls in the drawer

The v2.2 drawer header gets an action row beneath the tally:

```
◉ media                              12 containers · 9 launchable · 12/12 online   ×
[ UP ⏻ ]  [ DOWN ⏻ ]  [ EDIT COMPOSE ⌘ ]                            last change 4d ago
```

- `UP` proposes `stack.up`. `DOWN` proposes `stack.down`. Both go through the normal approval
  path and land on Actions as a Flight Authorisation card — nothing executes from a click.
- **Disable, never hide.** `UP` is disabled with a `title` when every service is already online,
  `DOWN` when none is. A control that vanishes teaches nothing; a disabled one with a reason does.
- **`DOWN` is the dangerous one and should read like it.** Warn-tinted, and the approval card
  names the services it will stop. `stack.down_all` and `stack.down_ingress` are **never**
  reachable from the UI at any width — those exist for the planner and for Telegram.
- `last change` comes from the compose file's mtime, which core already stats.

**Mobile:** the three buttons become a full-width stack under the header, `DOWN` last.

## 2 · The compose editor

`EDIT COMPOSE` opens a full-height editor, same shell as the Config tab — 44px gutter, mono
11px/1.7, `wrap="off"`. Reuse `.config-editor-shell` and its three-layer contract rather than
building a second editor; if the two ever need to differ, factor the shell out instead of
forking it.

Differences from the Config tab:

- **No locked-line tints.** Nothing in a compose file is key-locked; the refusals here are about
  the artifact as a whole, not about individual lines.
- **The footer reads `PROPOSE CHANGES`, not `CHECK`.** A compose edit cannot be checked in
  isolation the way config can — what validates it is `edit_runbook()` building a runbook, which
  is the same call that proposes it. One button, one refusal path.
- **A refusal is the common case, not an error state.** `parse_services` refuses anything that is
  not a compose document with at least one service; `check_lan_only` refuses a router rule that
  would publish a LAN-only host to the public domain; `_check_target` refuses a path that is not
  the stack's own compose file. Render the reason verbatim in a crit card above the footer — these
  messages are written to be read by the operator.

### The one thing that must not be lost

`edit_runbook()` takes `current_content` and turns its hash into the `compose.write` step's
`expected_old`. That is a compare-and-swap: if the file changed between opening the editor and
approving the plan, the write refuses rather than clobbering. **The editor must send back the
content it loaded, not just the new text**, or that protection quietly becomes a no-op.

Dockge has no equivalent — two tabs open on the same stack is a last-write-wins race there.

Pass `expect=[...]` with the service names the operator's edit is about when the edit came from a
finding or an incident (the caller knows), and omit it for a free-form edit (the operator does not
owe us a declaration).

### Reading the file

The dashboard's user cannot read the stacks tree, the same way it cannot open the actions
database. **The compose file comes over RPC from core**, like `config.get` already does:

```
GET  /api/stacks/<stack>/compose   →  core "stack.compose_get"  →  {text, sha256, path, mtime}
POST /api/stacks/<stack>/compose   →  core "stack.compose_propose"
                                      body: {text, base_sha256, expect: []}
                                      → {approval_id} | {refused: "<reason>"}
```

`base_sha256` is what the editor loaded. Core resolves it to the text it hashes from disk and
hands `edit_runbook()` both halves — the browser never supplies `current_content` itself, or a
stale tab could talk the core into a swap it did not intend.

### After proposing

The editor closes to a receipt: `PROPOSED · awaiting authorisation` with a link to the Actions
tab. The approval card shows the artifact `edit_runbook()` recorded (`runbook.artifacts` is keyed
by content hash), so what gets approved is the exact bytes that will be written — not a summary
of them.

## 3 · Where this leaves the Config tab

Two editors, two different things, and the distinction is worth keeping sharp in the copy:

- **Config** edits Planet Express's own behaviour. Sensitive keys are locked and the lock is
  enforced by core.
- **Compose** edits what runs on the host. Nothing is key-locked; the whole artifact is approved
  or refused.

Same shell, same keyboard feel, different verbs and different refusals.

## Retiring Dockge

Same shape as the homepage checklist in v2.2, and the same rule: **nothing is removed until the
thing that replaces it is in front of you and working.**

- [ ] `UP` / `DOWN` propose, and the resulting card executes cleanly on a real stack
- [ ] A compose edit round-trips: open, change, propose, approve, `stack.up`, services recreated
- [ ] A stale-tab edit is refused by the compare-and-swap, with a message that says so
- [ ] A malformed file is refused with its parse error visible
- [ ] The `dockge` router is removed from Traefik and drops out of the routing matrix
- [ ] Remove the `dockge` container and its stack

Until that list is green, Dockge stays. Removing it early does not fall back to the dashboard —
it falls back to SSH.
