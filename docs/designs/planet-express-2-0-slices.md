## Problem Statement

Planet Express (v1.1.0, ~8k LOC Python) is a safety-bounded sysadmin agent for a Docker Compose
homelab, used by its author and 1-2 others. All operational power lives in Telegram: 16 commands in
`casa_farnsworth.py:handle_message()` plus ✅/❌ approval callbacks. The Scruffy dashboard
(`casa_scruffy.py`) is read-only by design; its "Approve" button is a `t.me` link.

There is no second server. The goal is to design and build 2.0, then migrate the **existing live
host** to it in place, refactoring toward the 2.0 brief's architecture **and** giving the
dashboard everything Telegram can do, plus three new powers: ask-anything chat, live logs with
container drill-down, and config editing.

The tension: Scruffy is safe today *because* it can do nothing. Worse, that safety is weaker than it
looks. Both `casa-dashboard` and `casa-planetexpress` run as the same `$RUN_USER`, which `deploy.sh`
requires to be in the `docker` group, so today's dashboard process is already root-equivalent. Bolting
Telegram's handlers onto it would add a second privileged path, exactly what the brief says to
eliminate ("Every interface uses the same safety boundary").

## What Makes This Cool

Open the dashboard on your phone over Tailscale, ask "why is Sonarr unhealthy?", watch Amy pull
evidence with read-only tools, get a proposed fix as a typed action with its risk class, tap
Approve, and see verification prove the container actually recovered. The same approval card appears
in Telegram; whichever of you taps first wins, exactly once, and the other card updates to say who.

## Constraints

- Locked (CLAUDE.md): Docker Compose only; git clone + systemd install, not a container; brain stays a
  standalone daemon, not an MCP server.
- Standing process: Codex second-review gate on anything touching `casa_bender.py` safety or
  `casa_farnsworth.py` planning/approval.
- Small user base (author + 1-2): multi-user means "who approved", not RBAC.
- Dashboard reached over VPN/Tailscale, with a login (D1).
- Compose editor explicitly not chosen (D2).
- Reuse ladder: no new dependency where Flask/Werkzeug or stdlib covers it.
- **Visual source of truth:** `docs/designs/planet_express_design_v20/`. It has the `cockpit.css`
  token system, `ACTION-SCREENS.md` (login, container detail, approval, execution: 20 states), and
  `DATA-CONTRACT.md`. The reference `.dc.html` files are ground truth for spacing and state
  treatment; their markup is never copied into templates.
- **Single live host.** No spare server: 2.0 lands on the production homelab in place, one slice at
  a time. Every slice is rehearsed first on a local full-VM test homelab (eng review D2, issue 8).

## Premises (agreed)

1. **P1 One safety boundary.** Telegram, Scruffy, and later MCP are thin front ends over one
   internal `CommandService` → policy → approval → Bender. No front end calls Bender or runs docker.
2. **P2 Chat is Amy's front door.** Chat investigates with read-only (R0) tools and can only
   *propose* a plan, which becomes the same approval object Telegram gets. Not a general chatbot.
3. **P3 Sudo scope stays out of the UI.** Config UI edits `paused_containers`, `forbidden_stacks`,
   `exclude_services`, and (once slice 3 adds them) autonomy levels, with diff + confirm.
   `sudo_allowlist` is display-only, matching `/grant` today.
4. **P4 Scruffy stays key-less, enforced by the OS (revised after Codex + spec review).**
   - **Separate identity:** Scruffy runs as a dedicated `planetexpress-web` user, **not** in the
     `docker` group, with read-only access to code, venv, and the state dir (`dashboard_data.py` still
     reads JSON snapshots) and no write access to any of them.
   - **Install location: unchanged, no move (outside voice T1).** Slice 1 grants
     `planetexpress-web` read access in place:
     - `setfacl -m u:planetexpress-web:x` on each directory from `/` to the clone that it can't
       already traverse;
     - `setfacl -R -m g:planetexpress-web:rX` on code and venv;
     - on `state/`, the same grant for existing files plus a default ACL
       (`setfacl -d -m g:planetexpress-web:rX`) so new snapshots stay readable.

     No write access anywhere. `deploy.sh` applies the grants idempotently.
   - **Socket:** core listens on `/run/planetexpress/core.sock`. Group `planetexpress-rpc` contains
     only `$RUN_USER` and `planetexpress-web`. Core unit sets `RuntimeDirectory=planetexpress`,
     `RuntimeDirectoryMode=0750`, `SupplementaryGroups=planetexpress-rpc`. Core unit also sets
     `UMask=0007` for the socket's creation (T2), so the socket is created `0660` by `bind()`. Core
     then `chgrp`s it to `planetexpress-rpc` and only then calls `listen(16)`. If either step fails,
     the RPC server does not start. Core checks the peer uid with `SO_PEERCRED`
     against `planetexpress-web`'s uid and rejects anything else.
   - **Unit hardening** on `casa-dashboard`: `NoNewPrivileges=yes`, `ProtectProc=invisible`,
     `ProtectSystem=strict`, `PrivateTmp=yes`, `SupplementaryGroups=planetexpress-rpc`; gunicorn runs
     with `--worker-tmp-dir /dev/shm` so worker heartbeats never need a writable `/tmp`.
   - **Protocol:** fixed method allowlist, request IDs, short calls only; long work runs on a core
     worker and is polled (see slice 1).
   - **Web:** production WSGI server (gunicorn, replaces Flask dev server at `casa_scruffy.py:70`);
     passphrase + 6-digit TOTP login (design v20 "Airlock"); CSRF token on every mutating route; `SameSite=Strict` session cookie.
   - **Approvals:** atomic, one-use, 60-minute TTL (design v20), recording `decided_by` and `requested_via`.
   - **LLM spend:** daily quota on chat-triggered LLM calls, enforced in core.
   - **Logs:** bounded cursor reads (slice 1 spec), never `docker logs -f` (Bender forbids
     `--follow`, `casa_bender.py:391`); secret redaction before output leaves core.
5. **P5 Core is host-neutral.** Host-specific checks now in core (DAM queues, gluetun
   port-forwarding, Unraid NFS fsid) become optional adapters/config. **Lower priority now:** the
   migration target is the same host, so these checks keep applying; P5 moves to slice 6. Hardcoded
   host paths to lift into config then: `casa_leela.py:474` (`/home/casaroot/stacks/network/.env`),
   `casa_leela.py:755`/`:757` (Traefik dynamic and certs dirs under `/home/casaroot/apps`), and the
   planner prompt example at `casa_farnsworth.py:179`.
6. **P6 Logs and drill-down are R0.** Restart/recreate buttons are typed actions through policy,
   never shell or `exec` into a container.

## Cross-Model Perspective (Codex)

- **Challenged P4** as under-specified: a unix socket limits reachability but provides no method
  authorization, CSRF, replay resistance, backpressure, quotas, or redaction. Verified against code:
  `notifier.py:1` excludes inbound commands; `casa_farnsworth.py:812` spawns threads around a
  singleton state; `casa_bender.py:391` rejects log following. → P4 revised.
- **Challenged core-first sequencing** as too serial (six core phases before any dashboard power).
  → Sequencing revised to vertical slices. Its "run 1.x on the new server now" rationale was later
  voided (there is no new server); slices still win because each lands on the live host
  independently instead of one big cutover.
- **Closest 50%:** Komodo (auth, container status, logs, audit). Rejected as a backend: its shell
  sessions and direct deploy controls are the alternate privileged path P1 forbids. Borrow UX only.
- **Coolest unconsidered idea:** "Holodeck mode", rehearsing a remediation on a sanitized replica
  before touching the host, and promoting proven fixes to runbooks. Deferred: needs incidents and
  verification to exist first, and NFS/secrets can't be faithfully replicated.
- **Key insight:** choosing ask-anything chat reveals the real itch is a conversational operations
  cockpit, not a button panel.

#### Behavior rules

- **Action details.**
  - `docker.logs_tail` runs `docker logs --timestamps --tail 500 --since <cursor> <container>`.
    The cursor is the RFC3339Nano timestamp of the last returned line. Lines at the cursor
    timestamp that were already sent are dropped by content hash.
  - stdout and stderr arrive merged; core sorts the chunk by timestamp before returning it.
  - A logs response is capped at 500 lines and 256 KiB. `--tail` returns the *newest* lines
    after the cursor, so if the cap is hit the response carries `skipped: true`. The view then
    shows an "earlier lines skipped" marker. "Load earlier" paging is deferred to a later slice
    (eng review D1). Gaps are always shown, never silent.
  - When the container restarts, the view shows a "container restarted" divider.
  - `docker.inspect_service` runs `docker inspect <container>` and returns only allowlisted keys:
    `State`, `RestartCount`, `Image`, `Created`, `Name`, `HostConfig.RestartPolicy`, `NetworkSettings.Ports`, and network IP/gateway/MAC (the design's healthcheck / restart policy / ports facts).
  - `Config` is never read. This replaces the LLM-format-string regex
    `_DOCKER_INSPECT_SAFE_FIELD_RE`, which stays in Bender for legacy diagnostics.
- **Operator-initiated actions (2026-09-15 decision).** When a logged-in operator taps Restart,
  the design's two-step confirm sheet is itself the approval.
  - Confirming calls one RPC method, `action.request`, which creates the proposal and an approval
    `decided_by=<operator>`, `requested_via="dashboard-direct"` in a single transaction.
  - It still goes through policy, target resolution, the mutation lock, execution, and
    verification.
  - Telegram gets an FYI message ("Hermes restarted media/sonarr"), not an approval card.
  - Agent- or LLM-originated proposals always need the approval card. Policy may later restrict
    which risk classes allow direct operator requests; in slice 1 only R1 does.
- **Action capabilities (2026-09-15 decision).**
  - Every registered action declares `abortable`, `rollbackable`, and `resumable`. All three are
    `False` for `docker.restart_service`.
  - The execution screen renders only the controls the action declares. For restart, `passed`
    offers DONE only.
  - `interrupted` offers RE-SCAN THE HOST and RE-PROPOSE. RESUME RUN never appears for a
    non-resumable action, and a consumed approval is never reused.
  - The design's ABORT, ROLL BACK, and FORCE ROLLBACK controls become live when an action that
    supports them lands (canary updates in slice 5).
- **Countdown vs server expiry.** The design pauses the countdown during submission. The server
  honours that by accepting a decision whose request arrived before `expires_at` even if
  recording it finishes after. It never trusts a client-supplied timestamp.
- **Proposal dedup.** One live proposal per `(action, target)`, where live means
  `status = 'pending' AND expires_at > now`. Rows past `expires_at` are marked `expired` lazily on
  lookup. A second `propose` from either front end returns the live proposal's ID; if none is live,
  a new proposal is created. Lazy expiry, lookup, and insert run in one `BEGIN IMMEDIATE`
  transaction, backed by a partial unique index on `(action, target_key) WHERE status = 'pending'`,
  so two simultaneous proposals from different front ends can't both insert. The criterion is "one proposal, visible in both front
  ends under the same ID," not two proposals that happen to match.
- **Approval routing.**
  - Typed proposals post a Telegram card via `notifier.request_approval(text, approval_id,
    kind="action")`. That method picks `TelegramClient.act_keyboard()` for `kind == "action"`,
    with buttons `act_ok:<approval_id>` and `act_no:<approval_id>`. Approval IDs are ≤ 16 chars,
    well under Telegram's 64-byte limit.
  - The returned Telegram `message_id` is stored on the approval row.
  - `interpret_decision` maps `act_ok` and `act_no` to `kind="action"`. `handle_callback` gains
    one branch for that kind, which calls `CommandService.approve/deny` and nothing else. The
    existing `plan` and `diff` branches are unchanged.
  - Dashboard decisions call the same method over RPC.
  - After any decision, `CommandService` updates the Telegram card:
    - for a Telegram tap, `notifier.resolve(decision, …)` as today;
    - for a dashboard decision, the new `notifier.update_request(message_id, text)`, which edits
      the stored message without a callback.
  - Either way the card reads "approved by X" or "denied by X". The dashboard card reflects it on
    its next poll.
  - `decided_by` records the dashboard username, or for Telegram `callback_query.from.id` (plus
    `from.username` when present), carried on a new `Decision.decided_by` field.
  - Typed proposals do **not** set `PipelineState.AWAITING_APPROVAL`, so a pending restart never
    blocks `/check`.
- **Lock rule: a mutation lock, not `PipelineState`.** Reusing `PipelineState` fails three ways:
  1. `state` and `transition()` each take the lock separately, so check-then-set races.
  2. A legacy plan can sit in `AWAITING_APPROVAL` with no TTL and would block typed actions for
     hours.
  3. Returning to `IDLE` clears the legacy pending plan.

  Instead:
  - `PipelineState` gains `try_begin_mutation(owner: str) -> bool` and `end_mutation(owner)`. A
    separate flag checked and set under one acquisition of the existing `_lock`; `_state` is
    untouched.
  - Every path that changes the host takes it:
    - typed execution;
    - legacy `_execute_plan` and `_do_rollback`;
    - `_run_update_pass` (`/patchnow`), which currently touches no state at all
      (`casa_farnsworth.py:1669`);
    - `update_scheduler_loop`'s weekly call to `zoidberg.run_update_pass`. If the lock is busy
      when the window opens, it retries every 5 minutes for up to 1 hour, then logs a skip and
      waits for the next window;
    - `maybe_run_safe_prune`;
    - `_run_stack_op`;
    - `apply_pending_diff`.

    None of these can overlap.
  - Approval order. First, a non-locking read of the approval row: if it's no longer `pending`,
    reply "already decided by `decided_by`"; if expired, reply "expired". The conditional UPDATE
    in step 3 stays the real guard.
    1. `try_begin_mutation("act:<id>")`.
    2. If false, reply "busy (<owner>), proposal still valid until <TTL>" without consuming
       the approval.
    3. If true, consume the approval atomically in SQLite
       (`UPDATE … WHERE id=? AND status='pending' AND expires_at>now`).
    4. If zero rows changed, `end_mutation` and reply "already decided/expired".
    5. Otherwise run execute + verify on a worker thread, and `end_mutation` in `finally`.
  - Deny never takes the mutation lock, works while busy, and uses the same pre-read and the
    same atomic conditional UPDATE (`pending → denied`), with the same "already decided" reply.
  - Typed approvals are therefore accepted while a legacy plan is `AWAITING_APPROVAL`, since
    they don't touch it, but never while anything is mutating.
  - Legacy paths that find the lock held reply "busy" the way `/patchnow` does today.
  - Legacy `plan`/`diff` callbacks call `try_begin_mutation` **before** `notifier.resolve` and before
    `transition(EXECUTING)`. On busy: answer the callback "busy, try again shortly" only, leave
    the card, the pending plan/diff, and `AWAITING_APPROVAL` untouched. This fixes today's order,
    where the card says "Bender is on it" before anything is checked.
- **Startup reconciliation (eng issue 7, lands in 1b).**
  - On core start, before the RPC server or Telegram polling begins, every non-terminal
    `executions` row becomes `interrupted` with reason "core restarted", and an event is recorded.
  - Telegram gets "interrupted, check `<container>`, re-propose if needed", and the stored card is
    edited via `update_request`.
  - The dashboard shows `interrupted`. The consumed approval is not revived; a new proposal is
    required.
